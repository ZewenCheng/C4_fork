2026-09-09用户反馈53.36，按紧邻交付消息关联到并行版；精确被评制品尚无回执绑定。该版比v2低7.49分、比v1低1.79分，没有同架构串行版评分可用于归因。成绩独立追加，固定包、标签及其创建时“未评分”记录保留；提速和七字段通过不代表评分提升。

GitHub 保存源码、配置、设计书、模型来源与清单、结果摘要、成绩来源和恢复说明。比赛图片、特征、线上逐图预测、凭证和运行缓存不进入公开仓库；精确结果快照保留在官方 `/workspace/work/c4-submission-versions/`，版本记录提供地址与 SHA-256。

每次拟提交前按以下顺序完成：

1. 固定版本名和精确运行产物，将代码、配置、设计书、`result.json` 与 `infer_time.json` 对应到同一版本。记录模型及清单摘要、数据版本和运行环境；若结果由后处理产生，应保留后处理前结果摘要与脚本版本。
2. 在官方工作区建立不可覆盖的独立快照，验证清单与文件摘要，并记录恢复位置。重跑输出若与旧结果不同，作为另一制品记录，不能覆盖已评分结果。
3. 在 `submissions/<version>/` 保存版本 JSON 和中文说明，引用或保存精确源码快照、设计书、模型清单以及结果摘要。大模型无需在每个版本重复上传，但其可恢复来源与固定版本必须明确；新增训练权重需另外验证合规的持久备份位置。
4. 检查 Git 差异、模型 LFS 待上传列表、敏感信息和必要验证，提交后推送 `main` 与该版本的固定标签。标签一经发布不移动；修正用新标签或新版本。
5. 从 GitHub 独立读取标签、提交和关键版本文件，确认远端内容及摘要。只有完成此步才可称“该拟提交版本已备份”；仅本地 commit 或正在上传均不算完成。
6. 得到评测成绩后追加带来源的记录，关联实际提交制品摘要和回执；保留旧分数。是否成为优选版本应结合相同口径验证、评分抖动和资源成本。

这些是 Agent 执行的交付约定，当前没有自动拦截平台上传的 Harness。正式提交前必须主动检查远端备份，不得把流程文档当成已执行证明。
